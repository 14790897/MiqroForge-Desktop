# 方案说明：harness 强制任务计划卡（#646-v2 Phase 2 核心）

## 一、背景（实测暴露的问题）

GPT 方案（2026-08-15 评审）定义 #646 = **任务计划决策点**：多步骤任务开始前弹一次计划卡，
执行中危险动作单独确认。实现 Phase 1 时计划卡的触发**依赖模型主动调用 `ask_user_plan_confirm`
工具**（提示词引导）。

**实测结果（2026-08-17）**：
- 第 1 次测试：模型调了旧工具 `ask_user_confirm_card`（没用新工具）→ 弹的是危险动作卡样式，流程顺序错
- 第 2 次测试：模型**完全不调用任何确认工具**，直接文本问「要不要保存成文档」→ 计划卡没出现

**结论**：模型主动调用**不可靠**（同一天两次行为不一致）——计划确认作为安全/协作机制，
**不能依赖模型自觉**。必须由 harness（平台侧）在任务级强制。

## 二、方案：harness 强制计划卡

### 核心原则（延续 GPT 三层模型）
```
用户 Mode → Agent Planning Layer（计划卡，#646）→ Safety/Approval → Execute
```
计划确认**是平台职责**（Agent Planning Layer），模型主动调是**优化**（提前展示好计划），
harness 强制是**兜底**（模型不弹就系统弹）。

### 触发判定（turn 启动，模型首轮回复后）
```
模型首轮回复
  ├─ 已调 ask_user_plan_confirm → 用模型弹的计划卡（正常流程，不重复）
  ├─ 无工具调用 → 纯文本回答，不弹
  ├─ 单工具调用（读类：search/read）→ 不弹
  └─ 其余情况 → 🔒 harness 强制弹计划卡
       ├─ ≥2 个工具调用（多步骤）
       ├─ 含写类（write_file/edit_file/apply_patch）
       ├─ 含执行类（exec）
       └─ 含上传/外发类（upload/qraft/支付）
```

### 计划卡内容（harness 生成，不依赖模型）
```
📋 AI 准备执行任务
  「用户请求摘要」（取自用户消息前 60 字）
  执行步骤：
    ① web_search — 搜索相关信息
    ② write_file — 写入文件
    ③ upload — 上传到外部平台
  需要权限：🌐 网络访问 · 📄 创建/修改文件 · ☁ 外部上传
  [取消] [开始执行]
```
- **步骤来源**：模型首轮回复的 tool_calls 序列（name + 参数摘要，工具描述映射成用户可懂短语）
- **权限来源**：按工具风险类推断（READ/WRITE/EXEC/UPLOAD → 权限清单）
- 模型没给步骤明细时兜底显示工具序列——**不阻塞**（用户看到"AI 要用哪些工具"即可）

### 流程对比
```
当前（Phase 1，模型自觉）：
  用户请求 → 模型 [可选]调 plan_confirm → 弹卡? → 执行
  （模型不调 = 无卡 = 静默执行——实测发生）

本方案（Phase 2，harness 强制）：
  用户请求 → 模型首轮回复 → harness 检测
    → 需弹卡 → 强制弹计划卡 → 用户[开始执行] → 放行工具执行
    → 不需弹卡 → 直接执行
  执行中：危险动作（上传）→ 单独 Action Card 确认
```

### 关键设计点
1. **弹卡时机**：模型**首轮回复**（含工具调用）后、**第一个工具执行前**——用户看到的
   是"任务开始前一次确认"，不是执行中打断
2. **一次性**：同一 turn 只弹一次计划卡（turn 级标记 `plan_card_shown`）——用户确认后
   后续工具不重复弹（危险动作除外——那是 Action Card，独立机制）
3. **与模型主动腿的关系**：模型主动调 plan_confirm → harness 检测到 `plan_card_shown`
   标记 → 不重复弹（去重）；模型不调 → harness 弹（兜底）
4. **单工具读类任务不弹**（search/read/分析）——不打扰高频小操作
5. **与 Approval 的关系**：计划卡（协作层）在前，审批（安全层）在后——计划确认后
   工具执行时审批仍按策略工作（协作模式文件自动、exec 确认）

### 实现落点
| 组件 | 改动 |
|---|---|
| `task_runner.py`（legacy turn 循环） | 首轮回复后插入检测：`_should_show_plan_card(tool_calls)` → 强制弹卡（复用 user_input_gate resolver 通道）→ 等待确认 → 置 `plan_card_shown` |
| `kun_runtime/loop.py`（KUN 循环） | 同样的检测点（KUN 路径） |
| 前端 | PlanCard 已就绪（复用——载荷 goal/steps/permissions 由 harness 生成） |
| `ask_user_plan_confirm` | 保留（模型主动优化路径）——harness 检测到已弹则不重复 |

## 三、待 ChatGPT 评审的问题点

1. **触发阈值**：≥2 工具调用 / 含写类 / 含执行类——这个"该不该弹"的判定够吗？
   要不要按 Mode 调整（协作模式弹、自动模式只弹上传类）？
2. **弹卡时机**：模型首轮回复后、第一个工具执行前——会不会太晚（用户希望看到计划
   再让模型开始想）？要不要在**模型开始思考前**弹（但那时还不知道模型计划）？
   折中：先弹"任务意图确认"（标题=用户请求摘要）→ 模型跑完规划展示详细计划？
3. **harness 生成计划的粒度**：只有工具序列（无步骤描述）够不够用户判断"同不同意"？
   需不需要模型在弹卡前先输出一段计划文本？
4. **一次弹卡 vs 多次**：长任务（10+ 工具）中途是否要二次确认（比如每 5 个工具）？
   GPT 之前说"只有两个打断"（开始一次+上传一次）——长任务要不要打破？
5. **自动模式**：GPT 定义"自主模式=授权最大自治，但危险边界仍在"——自动模式下
   计划卡还弹吗？（建议：自动模式计划卡不弹，仅危险动作弹——与 GPT 模式矩阵一致？
   还是自动模式也要计划确认一次？）
6. **与 #684 逐工具 gate 的关系**：本方案（任务级一次）与 #684（工具级每次）的区别
   确认——#684 冻结为技术验证，本方案是其演进。
